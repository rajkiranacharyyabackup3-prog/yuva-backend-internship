This report describes a local performance comparison for the blog API's post collection. The baseline is the existing `GET /api/v1/posts` route, which returns every post in one response. The Week 4 project adds a paged endpoint at `GET /api/v1/posts/page?page=0&size=20`. The original route and its response format remain available, while the new route caps the page size at 100 and returns a `hasNext` flag so clients can request additional results without loading the whole collection at once.

The comparison used a file-backed H2 database with 250 posts, each containing about 4 KB of body text, and one registered author. Both versions ran with Java 21.0.11 and Spring Boot 4.1.1 on the same local machine. Each run included 20 warm-up requests followed by 1,000 measured GET requests at concurrency 8. The load script recorded response status, duration, response body size, throughput, and Java process working-set and CPU samples. The raw per-request records are included as JSON and CSV files.

In this run, every request succeeded. The mean response body fell from 1,046,331 bytes to 83,761 bytes, a 91.99% reduction. Mean latency changed from 50.747 ms to 18.648 ms, p95 latency from 87.437 ms to 50.551 ms, and measured throughput from 156.07 to 424.50 requests per second. The report also includes working-set and CPU figures, test setup, and caveats. Because the paged response contains fewer records, this is a bounded-output comparison rather than an identical-payload benchmark. It is a local directional measurement, not a production capacity guarantee.
